# 企业级结构化文档架构设计提示词

## 一、任务目标

请为当前项目设计一套规范、清晰、完整、可扩展的企业级结构化文档架构（Structured Documentation Architecture）。

采用**分层式、编号式、职责驱动的文档分类架构**，以文档内容、业务领域、技术职责和工程生命周期为核心，建立统一的文档组织体系。

参考成熟的文档组织方法：

- arc42：架构文档组织规范。
- C4 Model：架构分层表达规范。
- Diátaxis：文档内容分类方法。
- ADR：架构决策记录规范。
- Docs-as-Code：文档版本管理理念。

不机械套用任何现成模板，应根据项目实际情况合理设计。

## 二、核心文档架构

采用数字编号与英文目录名称相结合的方式，建立统一的一级文档分类体系。

建议采用以下基础结构：

```text
docs/
├── README.md
├── 00-project/          # 项目管理
├── 10-architecture/     # 系统架构
├── 20-features/         # 功能设计
├── 30-contracts/        # 接口契约
├── 40-data/             # 数据设计
├── 50-security/         # 安全设计
├── 60-operations/       # 运维管理
├── 70-delivery/         # 项目交付
├── 80-ai/               # 专项技术设计
├── 90-reference/        # 参考资料
└── superpowers/         # 开发辅助规范
```

以上结构作为基础参考，具体目录应根据项目实际情况调整，不要求所有项目机械采用全部分类。

## 三、目录职责划分

### 00-project：项目管理

负责项目整体信息及管理类文档，包括项目背景、建设目标、需求范围、项目规划、开发规范及统一术语。

### 10-architecture：系统架构

负责整体技术架构及系统设计，包括架构概览、系统上下文、容器架构、组件架构、模块划分、技术选型、系统集成、部署架构及架构决策记录。

### 20-features：功能设计

负责功能需求和业务设计，包括功能说明、业务流程、业务规则、状态流转、功能边界、异常场景及模块设计。

### 30-contracts：接口契约

负责系统交互规范，包括 API 定义、请求响应结构、数据传输协议、事件契约、消息协议、错误码及接口版本管理。

### 40-data：数据设计

负责数据结构和数据管理，包括数据模型、数据库设计、表结构、字段字典、实体关系、索引设计、数据流转及数据迁移。

### 50-security：安全设计

负责安全体系设计，包括身份认证、权限控制、访问控制、数据安全、密钥管理、审计机制及安全策略。

### 60-operations：运维管理

负责系统运行和维护，包括环境配置、部署运行、日志管理、监控告警、故障排查、备份恢复及性能管理。

### 70-delivery：项目交付

负责交付和版本管理，包括发布规范、版本记录、交付清单、测试验收、部署检查及变更记录。

### 80-ai：专项技术设计

负责独立技术领域的专项设计。根据项目实际情况组织相关技术文档，不应将专项技术内容强行混入普通功能或整体架构文档。

如果项目不存在对应技术领域，可以不创建该目录。

### 90-reference：参考资料

负责技术参考、外部规范、第三方资料、调研报告、术语补充及相关技术文档。

### superpowers：开发辅助规范

负责开发过程中的辅助规范，包括开发工作流、编码约束、代码审查、测试规范、任务拆解及文档维护规范。

## 四、文档拆分与组织规范

### 1. 单一职责原则

每个目录只负责明确的文档领域，每份文档应有清晰的主题和用途。

### 2. 高内聚、低耦合原则

相关内容集中组织，不同领域保持合理边界，避免跨目录重复维护。

### 3. 文档粒度控制

- 内容主题独立且复杂时，拆分为单独文档。
- 内容关联紧密且规模较小时，合并管理。
- 需要独立维护、评审或引用时，优先独立成文档。
- 禁止为了追求目录数量而过度拆分。

### 4. 唯一事实来源原则

同一技术规范、业务定义或数据结构只能有一个权威维护位置。

其他文档通过相对路径引用，不重复复制完整内容。

### 5. 生命周期管理原则

文档分类应覆盖项目规划、需求分析、架构设计、功能设计、开发规范、测试验证、部署运行、维护升级及版本交付等阶段。

### 6. 可扩展原则

一级目录采用数字编号，预留编号间隔。

新增文档领域时，应优先评估现有目录是否可以容纳，只有职责边界明确且内容规模足够时，才新增一级目录。

### 7. 层级控制原则

建议最多使用三级目录：

- 一级目录：文档领域。
- 二级目录：具体分类或业务模块。
- 三级目录：细分主题。

避免无意义的多层嵌套。

## 五、文档命名规范

统一采用以下命名规则：

- 目录使用英文小写。
- 多个单词使用连字符连接。
- 一级目录采用两位数字编号。
- Markdown 文档使用 `.md` 后缀。
- 文件名称应准确反映文档内容。
- 禁止使用无实际含义的名称。
- 同一领域内保持命名风格一致。

## 六、文档导航规范

`README.md` 作为整个文档体系的统一入口。

必须包含：

1. 文档体系概览。
2. 完整目录结构。
3. 一级目录职责说明。
4. 二级目录导航。
5. 文档阅读顺序。
6. 文档维护规范。
7. 文档之间的关联关系。

目录内部可以根据实际需要增加独立的 `README.md`，用于说明该领域的文档组织方式。

## 七、架构设计质量检查

设计完成后，必须进行以下检查：

| 检查维度 | 检查要求 |
|---|---|
| 完整性 | 是否覆盖必要的文档领域 |
| 单一职责 | 各目录是否具有明确职责 |
| 边界清晰 | 是否存在目录职责重叠 |
| 合理拆分 | 是否存在过度拆分 |
| 内容归属 | 每类文档是否有唯一归属 |
| 扩展能力 | 是否支持后续增加文档领域 |
| 可维护性 | 是否容易查找和更新 |
| 一致性 | 命名、编号、层级是否统一 |

## 八、最终设计要求

请根据当前项目的实际情况，对基础结构进行优化，输出最终文档架构。

必须遵循：

1. 保留合理的基础分类，不随意改变成熟的目录职责。
2. 允许根据项目特点调整专项目录。
3. 不允许为了追求完整而创建无意义目录。
4. 不允许不同目录出现职责交叉。
5. 不允许将所有内容堆积在单一目录。
6. 不允许将具体技术实现限制为固定的目录体系。
7. 确保目录编号具有逻辑性和可扩展性。
8. 确保每个目录都有明确的内容边界。

**最终目标：形成一套职责明确、分类合理、层次清晰、易于导航、可持续扩展的企业级结构化文档架构。**

本任务只负责文档架构规划、目录分类、层级拆分及职责定义，不涉及具体文档内容编写和项目代码修改。
