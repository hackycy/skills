# Document Types and Composition

从读者 intent 选择主要文档类型。一个页面可以包含少量辅助内容，但不能让读者同时面对多个同等重要的阅读目标。

## Selection table

| Reader intent | 文档类型 | 主要结构 | 不应承担的内容 |
|---|---|---|---|
| 学会一个概念或能力 | Tutorial | 前置条件 → 学习路径 → 最小示例 → 解释 → 练习或验证 | 完整 API 清单、设计历史、所有边界案例 |
| 完成一个明确任务 | How-to / Runbook | 目标 → 前置条件 → 步骤 → 验证 → 恢复或下一步 | 长篇概念教学、未经验证的设计理由 |
| 精确查找事实 | Reference | 适用范围 → 定义 → 参数或行为 → 默认值 → 限制和例外 | 按故事展开的教学序列、实现过程 |
| 理解系统或设计 | Explanation / Architecture | 问题 → 组成 → 关系或流程 → 不变量 → 权衡 → 深入链接 | 可执行操作清单、逐行代码说明 |
| 理解并记录一次选择 | ADR / Decision record | 背景 → 决策 → 取舍 → 后果 → 验证或复查条件 | 把已确定的当前契约写成未来时态 |
| 遵守持续适用的规则 | Policy / Standing instructions | 适用范围 → 必须行为 → 例外 → 责任和依据 | 一次性计划、事故故事、实现流水账 |
| 了解一次事故或演变 | Postmortem / Changelog | 影响 → 证据或时间线 → 原因 → 恢复 → 后续改进 | 作为当前行为的唯一权威来源 |

## Composition rules

- Tutorial 和 How-to 按读者需要的前置知识和动作排序；完成一项后再引入下一项。
- Reference 按读者查找信息的维度排序，例如对象、操作、参数、返回值、错误和限制；不要按作者发现它们的顺序排列。
- Explanation 先建立系统边界，再说明组成、关系、数据流和不变量；把具体类型和接口交给它们的 owner。
- ADR 记录已经作出的选择及其后果；已实现的机制用当前时态描述，未决定事项明确标成开放问题。
- Postmortem 可以使用时间线，因为时间线是事故证据；不要把时间线写进普通当前状态文档。
- Policy 只写持续适用的要求。一次性迁移计划、验收清单和临时状态应放在对应的执行工件中。

## Mixed intent and splitting

当同一文档同时包含两种 intent 时，先判断辅助内容是否只服务于主要 intent：

- 若辅助内容很小，保留并明确标注其作用。
- 若辅助内容需要独立导航、独立维护或独立 owner，拆成单独文档。
- 拆分后，原文保留读者定位、选择标准和链接，不保留完整副本。

## Dependency ordering

写提纲时先列出每个章节依赖的术语、事实和动作，再进行拓扑排序。若发现后文才定义前文必需的概念，移动定义、降低前文复杂度或链接到更合适的前置文档。

不要将以下顺序直接当成文章顺序：调查顺序、实现顺序、提交顺序、会议讨论顺序或作者记忆顺序。它们可以作为 ADR 或 Postmortem 的证据，但通常不是 Tutorial、How-to、Reference 或 Explanation 的阅读顺序。

## Type-specific completion criteria

- Tutorial：读者能沿着路径获得目标能力，并能完成最后的验证。
- How-to：读者能执行步骤并判断成功、失败和恢复条件。
- Reference：读者能在不阅读完整叙事的情况下定位所需事实。
- Explanation：读者能解释组成、关系、不变量和主要取舍。
- ADR：读者能知道选择是什么、为何选择以及它带来的后果。
- Policy：读者能判断规则是否适用、必须做什么以及例外是什么。
- Postmortem：读者能区分影响、证据、原因、恢复和后续行动。
