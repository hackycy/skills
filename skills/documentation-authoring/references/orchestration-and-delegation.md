# Orchestration and Delegation

子代理是大文档的可选执行机制，不是文档写作的默认步骤。主代理先完成规划，再根据任务规模和独立性决定是否派发。

## Role split

### 主代理

主代理负责：

- 读取项目规则、文档树和权威事实来源。
- 建立并冻结 Document Contract 和 authoring plan。
- 划分工作单元，确认 owner、依赖、排除项和验收条件。
- 判断是否达到 dispatch gate。
- 派发任务、处理阻塞、合并结果并完成全局校验。

主代理始终拥有全局结构、事实归属、跨文档链接和最终写作质量。子代理不能通过局部任务改变这些决定。

### 子代理

子代理负责一个边界清晰的写作单元：读取指定来源，编写或更新指定章节/文件，并返回可合并的结果。子代理必须遵守主代理给出的 document type、scope、owner 和术语，不重新规划相邻章节。

## Dispatch gate

先判断是否存在“足够大的、可并行的工作”，再判断是否值得调度。

### 直接单代理完成

出现以下任一情况时不要派发：

- 只修改一个文件中的少量段落、一个章节或一个局部补充。
- 所有内容依赖同一个未解决的事实、决定或共享草稿。
- 工作单元之间高度串行，后一个单元必须等待前一个单元的完整正文。
- 多代理只会重复读取同一小段上下文，合并成本接近直接写作成本。
- 任务的主要难点是全局判断、取舍或冲突解决，而不是局部正文产出。

### 适合派发

满足以下大部分信号，并且至少有两个独立工作单元时可以派发：

- 文档覆盖多个子系统、多个章节或多个目标文件。
- 各章节可以根据不同的源码、配置、schema 或 owner 独立核实。
- 各工作单元有明确的输入、排除项和验收结果。
- 主代理继续承载全部源码和正文会显著增加上下文压缩或遗漏风险。
- 章节之间共享的是稳定术语和链接，而不是需要共同编辑的长段落。

“长”本身不是派发理由；可独立验收的边界和足够的上下文收益才是派发理由。

## Planning before dispatch

派发前先写出可供子代理执行的 authoring plan。计划可以是任务目录中的临时文件，也可以是主代理维护的明确工件，但必须包含：

- 全局 Document Contract 和目标文档类型。
- 章节/文件树及其依赖顺序。
- 每个工作单元的唯一 owner、目标路径和 scope。
- 可读取的权威来源和禁止复制的内容。
- 排除项、共享术语和跨单元链接约定。
- 完成条件、输出格式和阻塞上报格式。
- 合并顺序，以及哪些内容只由主代理编写。

如果计划仍在决定读者目标、事实 owner 或章节边界，不要派发写作任务。先由主代理继续调查或报告缺口。

## Task handoff

每个子代理任务只携带完成该单元所需的最小上下文：

```text
目标：完成哪个章节或文件
类型：Tutorial / How-to / Reference / ...
范围：必须覆盖和明确排除的内容
权威来源：源码、配置、决策记录或现有文档
依赖：必须先存在的章节、术语或链接
验收：完成后读者能做什么或查到什么
输出：补丁/正文、来源清单、未决问题、验证结果
```

不要把“请完善整篇文档”作为子代理任务。不要让两个子代理同时编辑同一文件或同一段落；共享文件由一个 writer 顺序处理，或由主代理统一合并。

## Result contract

子代理返回以下四类结果：

1. 修改后的文件或明确的正文片段。
2. 使用过的权威来源和新增链接。
3. 仍未解决的事实冲突、缺失来源或 scope 问题。
4. 与该单元完成条件对应的验证结论。

子代理不返回大段过程叙述，不把推测写成事实，也不声称验证了未实际检查的内容。

## Integration

主代理按 authoring plan 合并结果：

1. 检查每个结果是否仍在自己的 scope 内。
2. 统一术语、标题层级、交叉链接和当前/历史时态。
3. 解决重复事实和多个 owner；保留权威来源而非简单择一拼接。
4. 重新检查全局依赖顺序和读者路径。
5. 对整套文档执行最终 validation；不能把各子代理的局部通过视为全局通过。

任何单元失败时，主代理只重新派发该单元或改为本地修订，不让失败结果污染其他章节。只有所有单元结果被合并、阻塞被记录、全局校验完成后，任务才算结束。
