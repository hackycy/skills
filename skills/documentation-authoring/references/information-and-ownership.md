# Information Taxonomy and Ownership

先判断内容是什么，再决定它应该出现在哪种文档中。文件名不是信息类型，文档类型也不是事实来源。

## Information types

| 信息类型 | 典型内容 | 首选 owner | 文档中的处理 |
|---|---|---|---|
| 当前契约 | API、类型、默认行为、错误、限制 | 源码、schema、配置或其 owning reference | 写稳定契约；不要复制实现细节 |
| 设计理由 | 为什么这样选择、放弃了什么、适用条件 | ADR、decision record 或实现后的 Agent Note | 写决策和后果；不要混入普通当前状态说明 |
| 操作步骤 | 如何配置、运行、迁移、排障或验证 | How-to、runbook、cookbook | 按可执行顺序写，并给出完成条件 |
| 学习路径 | 从前置概念到可独立完成的能力 | Tutorial | 按依赖和难度递进，只引入当前步骤需要的概念 |
| 概念解释 | 组件关系、数据流、架构模型、权衡 | Explanation、architecture 或概念页 | 解释关系和不变量；链接到具体 owner |
| 查询资料 | 参数、选项、事件、错误码、字段、兼容性 | Reference 或生成的 reference | 按查询维度组织；生成来源优先 |
| 持续规则 | Agent、贡献者、运行维护者必须遵守的行为 | Policy、`AGENTS.md` 或项目治理文档 | 写持久规则和范围；不要写故事或一次性计划 |
| 事故与历史 | 影响、时间线、根因、恢复、演变 | Postmortem、Changelog 或历史记录 | 明确标记为历史；不要让它成为当前契约的 owner |
| 生成事实 | 自动生成的目录、状态、清单、API 表 | 生成器和其输入源 | 链接或重新生成；不要手工维护副本 |

## Canonical owner rules

1. 先查源代码、配置、schema、生成器、已有 reference 和 decision record，再决定是否新增内容。
2. 事实 owner 只保留一处完整定义；其他位置只保留定位所需的摘要和链接。
3. 文档可以拥有解释、教程流程和面向读者的契约，但不能因为读者方便而夺取源码或生成器的事实所有权。
4. 如果两个来源都声称拥有同一事实，记录冲突、列出证据，并停止猜测；不要用最新编辑时间替代权威判断。
5. 如果事实变化频繁，优先让环境或生成器成为 owner，并在文档中说明如何查询或刷新它。

## Scope ownership across a tree

父级文档负责定位、组成、职责和高层行为。直接子级负责自身的类型、参数、语义、测试机制、操作细节或实现契约。父级可以说明“这里有什么”和“何时阅读子级”，但不复制子级的细节。

测试机制、fixture、harness、生成目录和具体配置属于能解释它们的最低 owning level。文档层级不会因为读者需要背景而自动获得更低层级的细节所有权。

## Ownership audit

对每个非平凡事实问三个问题：

- 谁能最早、最可靠地发现它已经变化？
- 哪个位置负责完整定义它，而不是只做摘要？
- 当前文档是否在复制该定义，还是只提供读者需要的入口？

若第三个问题的答案是“复制”，删除副本并链接 owner。若第一个或第二个问题没有答案，先补足权威来源或报告缺口，再继续写作。
