# Writing and Validation

这一份参考负责把已确定的类型、owner 和 scope 转成可读正文，并检查文档是否仍然承担正确职责。

## Expression rules

- 直接写事实、动作、条件和结果；删除“本节将介绍”“下面我们来看”等不增加信息的元话语。
- 优先使用主动语态和具体动词，例如“返回”“缓存”“跳过”“抛出”“链接”。
- 首次出现术语时给出最小定义，后续保持同一名称；不要为了变化而替换稳定术语。
- 明确区分“必须”“默认”“推荐”和“可以”；把建议的适用条件和不适用条件一起写出。
- 先写默认行为，再写例外；先写可观察行为，再写内部原理。
- 用能说明目标的链接文字链接到 owner、子文档、源码和决策记录。
- 每个段落只承担一个主要信息；并列选项、条件、限制和步骤使用列表。
- 代码、命令、输出和对应解释保持相邻；示例只保留当前概念需要的部分。
- 只在读者需要时加入背景、取舍和深入原理；不要用长篇解释包围一个可直接查询的事实。
- 当前状态用当前时态表达。理由、演变、事故和变更过程只放在承担这些职责的文档中。

表达规则受文档类型约束：示例优先适合 Tutorial 和 How-to；Reference 优先可检索性；ADR 优先决策和后果；Postmortem 优先证据和时间线。

## Structural validation

按以下顺序检查，发现前一层问题时先修复它，不要用语言润色掩盖结构问题：

1. **Authority**：每个非平凡事实都有唯一 owner；源码、配置或生成器拥有的事实没有被手工复制。
2. **Intent**：文档有一个主要 reader intent，标题、开头和结构都服务该 intent。
3. **Scope**：所有章节都属于 Document Contract；下层细节已移动到 owner 或通过链接引用。
4. **Dependency**：术语、前置条件和必要事实出现在使用之前；文章没有按发现或实现顺序展开。
5. **State**：当前契约、设计理由、历史叙事和一次性计划没有混成同一职责。
6. **Composition**：结构符合文档类型，且每个主要章节有可判断的结果或查询价值。
7. **Links**：链接指向权威细节，链接文字说明目标；删除失效、重复或无法证明用途的链接。
8. **Durability**：删除会过时的状态缓存、实现流水账和无证据的推测；保留能帮助未来读者理解和行动的稳定信息。
9. **Expression**：主体、动作、条件、默认值、限制和例外明确；没有空泛评价、段落墙或术语漂移。
10. **Completion**：读者能完成该类型的目标，或能明确找到下一层 owner；仍未解决的事实冲突已被报告。

## Slop patterns

发现以下模式时，优先移动、删除或链接，而不是继续扩写：

- 同一事实在多个文档中完整出现。
- 父文档重新讲解子文档的类型、参数、测试或实现细节。
- 当前状态文档出现“以前、现在改为、不再、曾经”等历史叙事，但没有历史文档承担它。
- 手工维护本应由源码、配置或生成器产生的目录和清单。
- 一个页面同时承担教学、查询、决策记录和事故复盘，而且读者无法判断入口。
- 文章按调查、实现、提交或讨论过程展开，导致依赖关系断裂。
- 用“强大”“灵活”“最佳”等评价词代替具体能力、限制和取舍。
- 用“更多信息”“点击这里”“后面会介绍”代替直接链接和明确目标。
