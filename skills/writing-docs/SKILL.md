# 文档写作

## 概述

像坐在读者身边的同事一样写，一次只解释一个概念。

用一句话定义，再立刻给最小示例，只解释读者刚刚看到的内容，最后给出下一步链接。

## 何时使用

适用于：

- 框架或库的指南文档
- 教程和 how-to 页面
- 需要叙述性解释的 API 文档
- 重写过于生硬、学术化或营销化的开发者文档

不适用于：

- 法务、政策或发布说明
- 几乎没有叙述正文的纯参考表格

## 先核实实现

把代码库视为行为事实的来源。不要根据 API 名称、已有文档、框架惯例或看似合理的架构推测实现。

开始写作前，按目标文档涉及的功能建立最小证据链：

1. 阅读适用的 `AGENTS.md`或`CLAUDE.md`、目标读者已有文档和项目约定。
2. 找到公开入口、导出或命令，并沿相关调用链读到能说明行为的实现。
3. 只在相关时阅读现有测试、配置、类型定义和示例；用它们确认边界、默认值和使用方式。
4. 搜索功能名、API 名和关键术语，找出直接相关的现有文档。

只探索目标功能及其依赖，不做无目标的全仓扫描。

对每项要写入的行为、限制、默认值和错误处理进行判断：

- 能由实现、现有测试、配置或类型定义证实，才写成事实。
- 现有文档与代码冲突时，先读代码确认，再以代码证据决定如何更新。
- 代码不能严谨回答，或证据彼此矛盾时，向用户提出具体问题；不要把推测写进指南。

## 大型文档的实现调研

当文档覆盖多个相互独立的模块、公开 API，或相关源码会明显挤占主代理上下文时，启动只读子代理调研实现。单一功能或小范围改写时，直接在主代理中查阅，避免拆分带来的协调成本。

按功能边界拆分任务，避免多个子代理重复阅读同一调用链。每个子代理只查找代码和现有文档，不修改文档、代码、测试或夹具，也不撰写面向读者的指南。

给每个子代理明确指定功能、目录或入口，以及需要回答的问题。要求它回传简洁的证据包，而不是大段源码：

1. 公开入口、导出或命令及其文件路径和符号名。
2. 每项已确认行为的实现路径、关键控制流和对应文件位置。
3. 已确认的输入、输出、默认值、错误处理、限制和相关配置。
4. 可复用的真实调用或已有测试用法，并说明其文件角色。
5. 无法由代码严谨确认的内容、证据冲突和需要继续追查的位置。

主代理根据证据包规划和编写文档。报告之间有冲突、缺少实现定位或无法支持待写主张时，继续追问对应子代理或读取该处源码；不要把子代理的概括当成未经核实的事实。只在最终文档需要时读取最小必要片段，不把大段源码搬入主上下文。

## 核心节奏

每个概念尽量遵循这 5 步：

1. 用一句平实的话点出它是什么。
2. 给出最小、可核实的示例。
3. 具体解释这段示例做了什么。
4. 再补一层细节：边界情况、可选方案或心智模型。
5. 用下一步操作或深入链接收尾。

如果连续两段都没有代码、输出结果或具体命令，这一节通常就太抽象了。

## 示例来源

优先使用项目中的真实调用、测试中的既有用法或已验证的公开接口。说明代码片段对应的文件角色，必要时标出文件名。

需要编写最小示例时，只使用已确认存在的公开接口和行为。只有实际执行过或项目已有验证覆盖时，才称其为“可运行”；否则说明所需运行条件。

不要为了文档新增测试代码、测试夹具或虚构 API。可以运行已有的相关检查，但不得以未验证的示例替代实现证据。

## 写作风格

### 直接、平静

对读者用“你”，在带着读者一起判断或操作时用“我们”。

- 推荐：“我们先看一个最小示例。”
- 避免：“本节将对该机制进行介绍。”

语气要稳、要实用，不要兴奋，也不要宣传。

### 先示例，后解释

代码是重心，文字要围着读者眼前这段示例展开。

- 推荐：“上面的 `computed()` 声明了一个基于 `author.books` 的计算属性。”
- 避免：在第一个可见示例之前先讲内部实现

### 渐进展开

只介绍当前页面已经铺垫到的概念。

- 先讲默认情况。
- 等读者建立起基本模型后，再补限制和例外。
- 深层原理用链接带走，不在当前段落里展开。

### 尊重读者

承认复杂性，但不要居高临下。

- 推荐：“关于这一点，现在知道这些就够了。”
- 避免：“这个很简单” / “显然”

## 章节模板

### 介绍一个概念

~~~md
## X 是什么？

X 是……

先看一个最小、可核实的示例：

```js
// code
```

这段代码展示了……
~~~

### 呈现多个选项

~~~md
## 该选哪个？

两种方式都能完成你的目标。

- 如果你想要……，选 A。
- 如果你更在意……，选 B。
~~~

### 收尾一个章节

```md
关于 X，目前知道这些就够了。准备好之后，继续阅读 [Y](/link)。
```

## 结构规则

- 每段控制在 1 到 3 句话。
- 标题尽量直接回答“这一节能帮读者做什么”。
- 选择、限制和结论优先用列表表达。
- 警告信息放进提示块，不要埋在正文里。
- 重要章节结尾都给出下一步、相关页面或具体动作。

## 文档一致性

当问题可由代码库严谨回答时，先查实现再回答。不要把另一篇文档当成行为证据。

发现相关文档可能与实现不一致时，先通过代码确认差异。更新当前任务指定的页面和直接关联页面；超出任务范围但已确认的问题，明确列出，不凭猜测扩大修改范围。

## 常见问题

| 问题 | 更好的写法 |
|---|---|
| 例子出现前铺垫太长 | 在首屏内给出最小示例 |
| 过早解释内部实现 | 先解释读者当前能观察到的现象 |
| 根据命名或惯例猜测行为 | 读取入口、实现和相关配置后再下结论 |
| 把现有文档当成实现依据 | 用代码确认，再处理文档差异 |
| 为文档临时新增测试 | 使用已有验证；不要增加测试代码或夹具 |
| 大型调研把整段源码交给主代理 | 让子代理回传带路径和不确定项的简洁证据包 |
| 把一种“最佳做法”写成放之四海皆准 | 按读者目标给出选择规则 |
| 用“强大”“优雅”这类形容词 | 直接展示结果，让示例自己证明 |
| “后面我们会讲……”这类前向引用 | 直接链接到后续页面 |

## 发布前检查

- 每个概念是否都先用平实语言定义，再逐步展开？
- 每个重要章节是否都尽早给出最小、可核实的示例？
- 解释是否始终锚定在当前可见的代码或输出上？
- 每项行为、限制、默认值和错误处理是否都有代码库证据？
- 大型任务是否按独立功能拆分为只读调研，并收到可追溯的证据包？
- 是否在文档与实现可能冲突时先查代码，再决定更新范围？
- 是否避免新增测试代码、测试夹具和未经验证的 API 示例？
- 全文是否避免了营销腔、被动语态和学术空话？
- 每个重要章节是否都告诉读者下一步该做什么？
