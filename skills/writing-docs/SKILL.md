# 文档写作

## 概述

像坐在读者身边的同事一样写，一次只解释一个概念。

目标风格接近 Vue 文档：先用一句话定义，再立刻给最小示例，只解释读者刚刚看到的内容，最后给出下一步链接。

## 何时使用

适用于：

- 框架或库的指南文档
- 教程和 how-to 页面
- 需要叙述性解释的 API 文档
- 重写过于生硬、学术化或营销化的开发者文档

不适用于：

- 法务、政策或发布说明
- 几乎没有叙述正文的纯参考表格

## 核心节奏

每个概念尽量遵循这 5 步：

1. 用一句平实的话点出它是什么。
2. 给出最小可运行示例。
3. 具体解释这段示例做了什么。
4. 再补一层细节：边界情况、可选方案或心智模型。
5. 用下一步操作或深入链接收尾。

如果连续两段都没有代码、输出结果或具体命令，这一节通常就太抽象了。

## 写作风格

### 直接、平静

对读者用“你”，在带着读者一起判断或操作时用“我们”。

- 推荐：“我们先看一个最小示例。”
- 避免：“本节将对该机制进行介绍。”

语气要稳、要实用，不要兴奋，也不要宣传。

### 先示例，后解释

代码是重心，文字要围着读者眼前这段示例展开。

- 推荐：“上面的 `computed()` 声明了一个基于 `author.books` 的计算属性。”
- 避免：在第一个可见示例之前先讲内部实现

### 渐进展开

只介绍当前页面已经铺垫到的概念。

- 先讲默认情况。
- 等读者建立起基本模型后，再补限制和例外。
- 深层原理用链接带走，不在当前段落里展开。

### 尊重读者

承认复杂性，但不要居高临下。

- 推荐：“关于这一点，现在知道这些就够了。”
- 避免：“这个很简单” / “显然”

## 章节模板

### 介绍一个概念

~~~md
## X 是什么？

X 是……

先看一个最小示例：

```js
// code
```

这段代码展示了……
~~~

### 呈现多个选项

~~~md
## 该选哪个？

两种方式都能完成你的目标。

- 如果你想要……，选 A。
- 如果你更在意……，选 B。
~~~

### 收尾一个章节

```md
关于 X，目前知道这些就够了。准备好之后，继续阅读 [Y](/link)。
```

## 结构规则

- 每段控制在 1 到 3 句话。
- 标题尽量直接回答“这一节能帮读者做什么”。
- 选择、限制和结论优先用列表表达。
- 警告信息放进提示块，不要埋在正文里。
- 重要章节结尾都给出下一步、相关页面或具体动作。

## 常见问题

| 问题 | 更好的写法 |
|---|---|
| 例子出现前铺垫太长 | 在首屏内给出最小示例 |
| 过早解释内部实现 | 先解释读者当前能观察到的现象 |
| 把一种“最佳做法”写成放之四海皆准 | 按读者目标给出选择规则 |
| 用“强大”“优雅”这类形容词 | 直接展示结果，让示例自己证明 |
| “后面我们会讲……”这类前向引用 | 直接链接到后续页面 |

## 发布前检查

- 每个概念是否都先用平实语言定义，再逐步展开？
- 每个重要章节是否都尽早给出最小示例？
- 解释是否始终锚定在当前可见的代码或输出上？
- 全文是否避免了营销腔、被动语态和学术空话？
- 每个重要章节是否都告诉读者下一步该做什么？
