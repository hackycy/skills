# 设计评审

对产品界面的视觉工艺和层级做严格、多轮评审。标准不是“能运行”或“网格对齐”，而是：一流产品设计负责人是否愿意为这个结果署名？

多数生成式界面是正确的，却没有被真正设计过：没有明确焦点、层级平坦、构图单调，看起来和任何其他应用一样。本评审要找出所有由默认值代替设计决定的地方，按影响定级，并给出明确结论。

**默认只评判。** 报告发现与结论，不修改代码。只有用户明确要求修复时才进入实施；评审与修改保持分离。

## 正确与精心设计之间

“正确”表示布局成立、元素对齐、颜色不冲突。“精心设计”表示每个决定都服务于意图，从整体构图到最后一个像素都被考虑过。评审的工作是找出从“正确”到“精心设计”的差距，而不是罗列个人审美偏好。

## 评审流程

按顺序完成五步。维度清单不能替代流程；先理解意图和整体，才能避免把个人口味误报成缺陷。

### 第一步：界定范围与意图

确定两件事：

- **评审对象**：当前构建、指定组件或分支中的 UI 变更。明确边界。
- **设计意图**：读取 `.product-interface-design/system.md`；若不存在，从项目和请求推断具体使用者、任务和感受。评审应对照设计自身意图，而不是通用理想。高密度交易终端不会因为高密度而失败。确实无法判断时，声明假设并使用通用工艺标准。

### 第二步：先看整体

像用户一样查看实际渲染结果。优先使用浏览器、截图或可用的内联渲染工具；实在无法渲染时，才从布局代码整体推断。

先回答：

- 是否有一个清晰焦点，还是所有元素同等竞争？
- 空间是否有张有弛，还是整页都是相同卡片和间距？
- 它是否明显属于这个产品，还是像任意仪表盘？
- 眯眼后层级是否仍成立，是否有元素刺眼地跳出？

最严重的问题通常存在于整体构图中，无法从单行 CSS 发现。

### 第三步：逐个使用评审镜头

每个镜头独立检查，核心问题始终是“这是决定，还是默认值？”

#### A. 层级

- 指出焦点。它是否通过尺寸、字重、对比或隔离真正胜出？
- 次要动作和元数据是否被同步降级？只有提升、没有降级，不构成层级。
- 不读文字时，是否仍能分辨主要、次要和元数据层？

#### B. 字体与颜色

- 层级是否同时使用尺寸、字重和颜色，而不是只改变字号？
- 是否有清晰比例字级，而不是任意的相邻字号？大标题是否适度收紧字距？
- 是否有四级文字色阶？动态数字是否使用 `tabular-nums`？
- 是否只有一个有意图的强调色，约占 10%，并用于状态、动作或身份？
- 表面是否在同一色相内改变亮度？色板是否来自产品世界？

#### C. 表面与深度

- 表面亮度变化是否轻微，边框是否低透明、可找但不抢眼？
- 是否只采用一种深度策略，还是临时混用边框和重阴影？
- 侧栏是否与画布同底色，只用轻微边界分隔？
- 嵌套圆角是否遵守 `outerRadius = innerRadius + padding`？
- 在脑中移除边框后，结构是否仍可通过空间和表面理解？

#### D. 构图与节奏

- 是否有密集区与开放区的节奏，还是卡片、间距和密度从头到尾完全一样？
- 布局比例是否表达关系？例如 280px 与 360px 侧栏传递不同的主次关系。
- 内容宽度是否经过选择，还是无差别铺满可用空间？

#### E. 状态、细节与动效

- 交互元素是否有 default、hover、active、focus、disabled？数据是否有 loading、empty、error？
- 点击区域是否达到 44×44px，最低 40×40px？图标和文字是否经过光学校正？
- 根节点是否启用字体平滑？标题是否使用 `text-wrap: balance`？
- 高频操作是否避免动画？其余 UI 动画是否通常低于 300ms、使用自定义 ease-out？
- 是否仅动画 `transform` 和 `opacity`，避免 `transition: all`？popover 是否从触发器方向展开？

#### F. 结构、复用与内容

- 是否重复实现项目或平台已有能力，例如用 `<div onClick>` 代替 `<button>`，或自行实现缺少键盘、焦点和 ARIA 的复杂控件？
- 是否绕过已有 Button、variant、组件库或语义 token，使用一次性长 className 和硬编码颜色？
- 是否用负 margin 抵消父级 padding、逃生式 `calc()` 或 absolute positioning 规避正常布局流？
- 页面中的标题、正文和指标是否讲述同一个产品故事？内容不一致会立即破坏可信度。

### 第四步：定级并过滤

为每个候选发现分配级别：

- **阻断**：使设计显得泛化或破损，不能通过批准标准。例如无焦点、平坦层级、单调构图、怯弱或竞争色板、缺失关键状态、结构性 hack、不可访问的自制控件。
- **应修复**：真实工艺缺口，但界面仍可工作。例如标题字距松散、边框稍重、单个圆角不一致。
- **提示**：影响轻微，只提一次，不扩展成愿望清单。

删除以下误报：

- 只是个人口味。选择与意图一致且执行良好时，不因评审者会选另一字体、颜色或布局而报错。
- 有理由且执行成功的大胆选择。鲜艳色板、戏剧性字级或不对称布局不等于缺陷。
- 超出既定范围，或在 diff 评审中属于未修改代码。
- 已由 `.product-interface-design/system.md` 确定的决定。
- 属于 lint、format 或 compile 的问题，它们由其他检查负责。

如果不能说明问题如何损害用户、层级或产品辨识度，它就是口味，应删除。少量高置信发现优于大量小意见。

### 第五步：报告与结论

按以下顺序排列发现：

1. 层级与焦点失败；
2. 使界面平坦的默认字体和颜色；
3. 表面、深度、构图和节奏问题；
4. 缺失状态、细节与动效问题；
5. 结构性 hack、重复实现和内容不一致。

每条发现必须说明：**什么使用了默认值**、**为什么它显得泛化或损害用户**、**应作出的具体设计决定**，并标注级别。引用可定位的文件和行号。存在渲染能力时，在报告末尾展示当前与改进方向的并排视觉；视觉中只呈现结果，推理留在文字中。

最后给出明确结论：**批准**或**不批准**。

## 批准标准

通过评审必须同时满足：

- 焦点明确，眯眼后层级仍可读；
- 字体由尺寸、字重和颜色共同建立层级；
- 强调色克制、有含义，并有领域依据；
- 表面分层安静、边框不刺眼，只使用一种深度策略；
- 构图有节奏，比例表达清晰关系；
- 状态完整，细节充分，动效有目的且通常低于 300ms；
- 复用项目组件和可访问原语，不存在缺少键盘、焦点或 ARIA 的自制复杂控件；
- 没有结构性 hack，内容叙事一致；
- 不会被误认为通用 AI 模板。

以下问题默认构成阻断，除非作者能依据意图给出充分理由：无焦点、仅靠字号的层级、默认字体、单调构图、怯弱或互相竞争的强调色、刺眼或割裂的表面、缺失关键状态、结构性 hack、应由成熟原语负责却不可访问的自制控件。

## 用户要求修复时

从设计决定重新推导被指出的部分，不要在默认方案上继续打补丁。先重建焦点、字体层级和表面系统，再处理数值细节；顺序为阻断、应修复、提示。超出聚焦修复范围的结构性重建应作为明确后续项，不做半成品改造。
