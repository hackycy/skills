# 回归评估场景

用于验证修改 skill 后，是否真的减少“中规中矩后台”而不是只改变视觉风格。每次大改后，用固定任务生成并截图比较。

## 场景 1：订单管理 Table-first

任务：设计一个每天处理数千订单的运营后台，支持搜索、筛选、批量修改状态、查看详情。

检查：是否避免 KPI 卡挤压主表；是否有 selection mode；详情返回是否保持上下文。

## 场景 2：退款审核 Queue

任务：设计退款人工审核台，需要风险信息、证据、Approve/Reject/Escalate，并连续处理下一条。

检查：是否形成 queue 而不是普通表格；处理后是否能进入下一条；风险动作是否匹配确认强度。

## 场景 3：客户 Object Workspace

任务：设计客户详情，包含账号状态、合同、最近活动、工单、付款与备注。

检查：是否围绕对象生命周期组织，而不是 12 张属性卡片。

## 场景 4：Incident Console

任务：设计 SRE incident 控制台，支持时间范围、服务筛选、严重级别、事件流、负责人和处理动作。

检查：是否建立多个 scanning anchors；是否避免巨大 KPI Hero；实时状态是否完整。

## 场景 5：自动化 Builder

任务：设计规则构建器，用户根据条件触发动作，并可测试规则。

检查：是否选择 Builder，而不是把条件做成表格；编辑与结果反馈是否并存。

## 场景 6：团队 Settings

任务：设计组织成员与权限设置，包含邀请、角色、SSO、安全策略和危险操作。

检查：是否按影响范围和任务分组；危险操作是否与普通配置分离；是否避免统一卡片堆叠。

## 评分方式

不要用单一“美观分”。逐项记录：

- Task path 是否更短；
- Archetype 是否匹配；
- Scan anchors 是否稳定；
- Search/filter/selection/detail 是否完整；
- State model 是否完整；
- 密度是否合理；
- 是否仍落回标准 dashboard 模板；
- 是否存在结构或交互层面的产品 signature。
