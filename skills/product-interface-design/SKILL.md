# 产品界面设计

为仪表盘、后台、SaaS 应用、工具、设置页、数据界面和交互产品做有明确取舍的设计。目标不只是“能用、对齐、颜色不冲突”，而是让每个决定都服务于具体的人、任务和产品世界。

本 skill 不用于营销页、落地页、活动页或纯品牌设计；这些任务应使用对应的营销或品牌设计能力。

## 模式路由

先判断用户要什么，只加载当前分支所需的参考文件：

- **设计或实现**：使用本文件完成探索、方向确认、实现和验证。
- **设计评审**：用户要求评审、审计、打分、批准或检查设计质量时，读取 [references/design-review.md](references/design-review.md)。评审默认只报告问题，不修改代码；只有用户明确要求修复时才实施。
- **去模板化**：用户要求去除 AI 味、设计套模板感或做局部视觉清理时，读取 [references/design-deslop.md](references/design-deslop.md)。该模式可以修改当前范围，但必须保持业务行为不变。
- **设计系统记忆**：需要新建设计系统文件时，读取 [references/system-template.md](references/system-template.md)；需要具体写法时，只读取与方向相符的 [精密与密度示例](references/examples/system-precision.md) 或 [温暖与亲和示例](references/examples/system-warmth.md)。
- **状态或模式提取**：用户询问设计状态时，读取并概括设计记忆；要求检查漂移时，对照它检查 UI 文件；要求提取模式时，扫描重复的间距、圆角、颜色和组件值，提出设计系统候选项，不直接保存。

## 先读现状

开始前检查现有应用、设计 token、组件库、样式约定和 `.product-interface-design/system.md`：

- 文件存在时，将其中的方向、尺度和组件模式视为已经确定的约束。新增设计应复用它们，除非用户要求改版。
- 文件不存在时，完成领域探索并提出方向；方向含糊或返工成本高时先让用户确认。
- 设计记忆只使用上述新路径，不读取或写入其他兼容路径。

## 先定意图

动代码前形成一份紧凑工作简报：

- **谁在使用？** 写具体的人与场景，不写抽象的“用户”。他们五分钟前在做什么，五分钟后要做什么？
- **必须完成什么？** 用动词表达核心任务，例如批改作业、定位故障部署、批准付款。
- **应该有什么感觉？** 使用能指导取舍的词，如“像工作台一样紧凑”“像阅读器一样安静”，而不是“简洁现代”。

若上下文不足以确定人、任务和感受，提出一个简洁问题；能够负责任地推断时，说明假设后继续。

意图必须贯穿整个系统。温暖不仅是背景色，还要体现在表面、文字、边框、语义色和字体；高密度也必须同时影响间距、字号和信息架构。对布局、色温、字体、间距和层级都要能回答“为什么”。“常见”或“能用”不构成理由。

## 产品领域探索

在提出视觉方向前产出以下四项：

- **领域**：至少 5 个来自产品世界的概念、隐喻或词汇，而不是功能清单。
- **色彩世界**：至少 5 种在该领域中自然存在的颜色、材质或光线，不只写“暖色”或“冷色”。
- **标志性元素**：一个只可能属于这个产品的视觉、结构或交互元素。找不到就继续探索。
- **拒绝的默认方案**：列出 3 个此类界面最容易落入的视觉或结构套路，并为每个给出有领域依据的替代方案。

检验方式：去掉产品名称后，别人仍应能猜出它服务的领域；否则探索不够具体。

提出方向时使用以下结构，并说明推荐理由：

```text
领域：      [至少 5 个产品世界概念]
色彩世界：  [至少 5 种领域色彩或材质]
标志性元素：[只属于该产品的元素]
拒绝：      [默认方案 → 替代方案，共 3 组]
方向：      [连接以上四项的设计方法]
```

方向昂贵或不明确时询问“这个方向是否合适？”。若会话提供内联渲染能力，同时展示小型视觉样本：实际色板、真实字体层级、表面层级和标志性组件。推理留在文字中，样本只展示视觉结果。

## 避开默认设计

默认方案常伪装成“基础设施”：

- **字体**不是内容容器。字重、标签性格和段落纹理在文字被读懂前就建立产品气质。
- **导航**不是脚手架。它表达当前位置、可达区域和优先级；漂浮的孤立页面只是组件演示。
- **数据**不是把数字放上屏幕。进度环、趋势线和堆叠标签可能显示同一数据，但叙事完全不同。
- **Token 名称**也在塑造产品世界。`--ink`、`--parchment` 有语境，`--gray-700`、`--surface-2` 只暴露模板。

如果类似提示交给另一个模型会得到几乎相同的结果，就说明设计仍由公共默认值驱动。差异应来自具体领域，而不是为了不同而不同。

## 视觉层级与构图

### 每个视图只有一个焦点

先说出用户进入这一屏最主要的动作或信息，再让它通过尺寸、字重、对比、位置或留白胜出。同步降级次要动作和元数据；只抬高焦点而不降级其他内容，仍然没有层级。

### 字级是比例，字重优先于尺寸

选择一个比例并保持一致：高密度或安静界面约 `1.2`，多数产品界面约 `1.25`，表现力较强时约 `1.333`。从 14–16px 正文推导完整层级，不使用 15/16/17px 这类难以辨认的微差。

使用尺寸、字重、颜色三项共同建立层级。一个 14px 字号也可以形成三层：值为 `600 / primary`，标签为 `500 / secondary`，元数据为 `400 / muted`。动态数字使用 `tabular-nums`。

### 密度、节奏和比例必须有含义

- 先确定间距基数和密度。工具面板 12–16px 内边距像工作台，24px 更像展示页；选定后保持一致。
- 不要让整页都是相同卡片、间距和密度。紧密控制区应过渡到更开放的内容区，相关内容靠近，组与组之间留出明显空气。
- 比例表达关系。280px 侧栏表示导航服务于内容，360px 侧栏表示两者更接近同等地位。
- 采用约 60/30/10 的分配：中性主表面、次级色调和不超过约 10% 的强调色。颜色用于状态、动作和身份，不用于无意义装饰。
- 优先用空间、字重和轻微色调变化分层，再考虑边框与分割线。

## 工艺基础

### 轻微分层

建立编号表面层级。暗色模式可从基底逐步增加约 7%、9%、12% 的亮度；亮色模式保持浅色，以柔和阴影表达高度。单独看每一级应接近不可察觉，叠放后层级才清楚。

- 侧栏与画布使用同一背景，以轻微边界区分，避免形成两个割裂世界。
- 下拉框和浮层比父表面高一级。
- 输入区是内凹接收内容的表面，通常应比周围略暗，而不是更亮。
- 边框在不寻找时应消失，需要结构时又能找到。暗色模式常用 `rgba(255,255,255,0.06–0.12)`，并为普通、柔和、强调和焦点建立渐进强度。

执行眯眼测试：模糊视线后仍能读出层级和分区，但没有边线或表面突兀跳出。

### 设计系统规则

- **颜色 token**：所有颜色映射到少量语义原语：前景、背景、边框、品牌、破坏性、警告、成功。避免随机十六进制值。
- **文字层级**：至少有 primary、secondary、tertiary、muted 四层，对应主要、辅助、元数据、禁用。
- **间距**：选 4px 或 8px 基数；微间距、组件内间距、区块间距和大区间距都从尺度派生。
- **内边距**：默认对称；只有内容结构确有需要时才不对称。
- **深度策略**：只选一种并贯彻：仅边框、轻微阴影、分层阴影或表面色差。
- **圆角尺度**：控件小、卡片中、模态框大。嵌套元素遵守 `outerRadius = innerRadius + padding`。
- **控件 token**：输入、选择和复选框拥有独立背景、边框和焦点 token，不与普通表面混用。
- **暗色模式**：弱化语义色饱和度，以边框代替无效的深色阴影；同一色相只改变亮度。

### 静态细节

- 每个交互元素实现 default、hover、active、focus、disabled；数据界面实现 loading、empty、error。
- 点击区域达到 44×44px，最低 40×40px；可用伪元素扩大可点击区，但相邻点击区不能重叠。
- 几何居中看起来不对时做光学校正，例如图标侧内边距约为文字侧减 2px，播放三角向右微移约 2px。
- 需要抬升的卡片、按钮和容器优先使用透明分层阴影；真实边框留给分割线和输入轮廓。
- 标题使用 `text-wrap: balance`，正文和说明使用 `text-wrap: pretty`，根节点使用 `-webkit-font-smoothing: antialiased`。
- 图片使用 1px 内描边：亮色 `rgba(0,0,0,0.1)`，暗色 `rgba(255,255,255,0.1)`。

### 动效

- 高频键盘操作不加动画；偶发的模态框、抽屉和 toast 使用标准动画；稀有或首次出现的时刻才增加表现力。
- 常规 UI 动画低于 300ms：按压 100–160ms，tooltip/popover 125–200ms，下拉 150–250ms；较大模态或抽屉可到 200–500ms。
- 进入和交互使用 `cubic-bezier(0.23, 1, 0.32, 1)`；屏内移动可用 `cubic-bezier(0.77, 0, 0.175, 1)`。避免 `ease-in`。
- 按压使用 `scale(0.97)`，不低于 0.95；出现从 `scale(0.95) + opacity: 0` 开始，不从 `scale(0)` 开始。
- popover 从触发器方向展开；模态框保持居中。
- 只动画 `transform` 和 `opacity`，明确列出 transition 属性，不使用 `transition: all`。
- 多项进入可错开 30–80ms，退出更快、更轻；遵守 `prefers-reduced-motion`。

## 复用项目现有能力

### 控件：原生元素 → 无样式原语 → 自行实现

1. 原生 HTML 能满足时直接使用 `<button>`、`<a>`、`<input>`、`<dialog>`、`<details>`，不要用 `<div onClick>` 伪装语义控件。
2. select、combobox、dialog、popover、tooltip、dropdown、tabs、date picker 等有复杂状态的控件，优先使用项目已有组件或成熟的 headless primitive，如 Radix UI、React Aria、Ark、Headless UI、Vaul、`cmdk`。
3. 只有没有合适原语或依赖预算明确禁止时才自行实现，并补齐方向键、Enter、Escape、焦点捕获与返回、ARIA、点击外部关闭和滚动锁定。

### 样式：系统 → 组件 → token → utility

1. 先复用现有设计系统、组件和 variant，并遵循项目已有的 Tailwind、CSS Modules 或 CSS-in-JS 约定。
2. 样式元素第二次真实复用时提取组件或 variant；不要提前抽象，也不要复制长 className。
3. 使用 `bg-card border-border text-muted-foreground` 一类语义 token，而不是 `bg-white border-gray-200 text-gray-500` 或随机字面量。
4. 内联 utility 只用于真正的一次性布局调整。

## 实施流程

1. 检查现有应用、设计系统、组件模式和设计记忆；完成条件是约束与可复用能力均已列明。
2. 完成领域、色彩世界、标志性元素和拒绝默认方案四项探索；完成条件是去掉产品名仍可辨认领域。
3. 确定布局、颜色、字体、密度、导航和焦点。绿地界面、重大改版或方向模糊时，如有图像生成能力，可生成方向板、UI 参考、截图 paintover 或栅格素材；图像只作为参考或资产，不能替代真实实现，也不用来生成图标、logo 或图表。
4. 必要时确认方向，然后使用项目已有组件和原语完成实现。
5. 运行相关 build、typecheck 和 tests。
6. 对非平凡 UI 做视觉验证。使用可用的内联渲染、浏览器或桌面与移动截图，修复重叠、断裂间距、空白状态、不可读文字、缺失素材和泛化构图。

写每个组件前，在内部明确以下检查点；只向用户展示有助于决策的结论，不倾倒长篇设计独白：

```text
意图：  [具体的人、任务、感受]
层级：  [焦点，以及它如何通过尺寸/字重/对比/空间胜出]
色板：  [来自领域探索的颜色及理由]
深度：  [边框/轻微阴影/分层阴影及理由]
表面：  [层级尺度及色温理由]
字体：  [字体与尺寸/字重/颜色杠杆及理由]
间距：  [基础单位与密度]
```

## 交付前检查

- **替换测试**：把字体换成常用默认字体、布局换成标准模板，结果是否几乎不变？不变之处仍是默认设计。
- **眯眼测试**：模糊视线后层级是否仍清晰，同时没有边线或表面突兀跳出？
- **标志测试**：指出至少 5 个具体位置体现标志性元素；“整体感觉”不算。
- **Token 测试**：只读 CSS 变量时，能否辨认产品世界，而不是任意项目？
- **状态测试**：交互状态与 loading、empty、error 是否完整？
- **响应式测试**：桌面和移动端是否无重叠、截断和不可达控件？

任一检查失败就继续迭代，再向用户展示结果。

## 保存设计记忆

任务完成后询问：“要把这些模式保存给后续会话使用吗？”只有用户同意后，才写入 `.product-interface-design/system.md`。使用 [设计系统模板](references/system-template.md)，记录：

- 方向与感受；
- 深度策略和间距基数；
- 字级比例、密度值和焦点模式；
- 使用两次以上、可复用或值得保留尺寸的关键组件模式；
- 影响实现的视觉参考、色板、比例与标志性元素。

设计记忆存在时，所有新增间距、深度、颜色和组件模式都必须与其一致；新的决定只添加到一个权威位置。
