# 设计约束与依据

Agent Notes 以 DeepSeek Harness Notes 的治理原则为基础：保留有长期价值的决策理由，维护仍指导工程的记录，并冻结只需追溯的历史。固定上游来源见[上游依据](upstreams.md)。

## 规划与记录分别判断

工作规模决定是否需要规划，长期理由决定是否需要 Note。进入原生 Plan 不代表同意创建文档；Agent 提出记录建议并获同意，或用户显式要求后才进入记录。一次授权覆盖同一工作范围。

只有代码、测试、现有文档无法解释的长期“为什么、放弃了什么”才需要记录。机械性或局部 UI 改动可零 Note 完成；代码量少但改变兼容性、持久化或责任边界时仍需评估。命中判据而尚无授权时应提出建议，不能自动创建，也不能静默遗漏。

先查现有决定，再准备普通 Markdown 草稿；内容完整后由 create/update 写入。草稿不是 CLI 生命周期，不生成空壳 Note、免写文件或会话台账。相同 topic 只是候选线索，不证明属于同一决定。

必要 Note 与相关代码在同一个 PR 交付，可以分布在多个 commit；不能代码合并后再补写。纯提案、拒绝或文档维护可以独立提交。没有 PR 时，以团队一起检查并集成的完整变更范围作为交付单元。

## skill 与 CLI 的分工

agent-note 在相关规划/首次编辑时查询 context，按返回指针读取正文，范围变化重查，交付前 check；获授权后再判断记录资格、复用与维护事实。agent-note-maintenance 负责替代、剩余价值、吸收、归档与条件清理。CLI 验证机械约束，作者与评审负责长期价值、同一决定和完整吸收的语义判断。

产品只管理项目 skill 与共享 runtime，所有 AGENTS/CLAUDE 文件由项目维护。具体宿主范围仅本地 CLI；静态资源不能证明 agent 已读、理解或必然调用。global、hooks、事件、插件、宿主版本适配及会话状态不属于本产品。安装模型和协议依据见[安装投影与恢复](integrations.md)。

## CLI 输入与交互边界

cac 集中声明命令、解析语法与生成帮助；Zod 校验 CLI 的类型、枚举和跨字段约束。cac 的缺值与未知参数检查不能代替这些约束。持久文档继续用 JSON Schema/Ajv 校验，CLI 输入模型不成为文档格式的新权威。

初始化的输入获取与确定性执行分开：显式值和已安装配置先解析，只有合格的交互终端才通过 Clack 询问缺项。脚本、JSON 和内容写命令保留确定性失败行为；提示走 stderr，stdout 保持结果协议。委派使用统一参数模型生成命令参数，不传递本地交互开关，也不提前消费写入 stdin。

问答可能长时间等待且用户可取消，因此收集输入前不能恢复事务或取得写锁。缺项的 install --recover 通过共享的 owner/journal/端点检查投影恢复后的只读快照：prepared 使用 before，committed 使用 after。回答后复查原始现场，再由安装器恢复并执行，避免中断安装的混合配置被当成已有项目设置。完整显式请求也先验证输入、来源与意图，再执行恢复。

## 生命周期选择

| 工程情形 | 行为与理由 |
| --- | --- |
| 尚未交付但已有完整提案 | proposed；已同意方向不等于实现完成，无需 accepted 状态 |
| 新决定已实现并验证 | 可直接创建 implemented，不强制先建 proposed |
| 同一提案交付 | 转 implemented，写实际决定、后果和验证 |
| 未采纳或停止推进 | 转 rejected，保留原提案和真实拒绝理由，无需 withdrawn 状态 |
| 路径或实现机制改变，决定不变 | 维护原 Note 的事实与作用范围 |
| 决定改变 | 新建并互链；partial/full 表达替代范围，proposed 替代只表示意图 |
| 已交付且仍能指导工程 | 保持活跃；完成本身不是归档条件 |
| 不再有未来指导价值，但值得历史追溯 | 归档 implemented；保留 implemented 元数据状态并冻结 |
| rejected 已无防错价值 | 提供理由并处理全部活跃引用后可清理 |
| implemented 的全部独有内容已被现行 owner 吸收 | 提供 coverage、承接者和引用去向后可清理 |

完整替代只表示旧决定不再执行，不证明其独有理由、替代方案、后果、验证和覆盖缺口已被吸收。部分替代的旧记录仍需维护剩余指导范围。不得以“Git 历史里还有”为由省略内容承接。

rejected 以 Git 基线保护原提案和拒绝理由，仅维护路由、关系和可验证为同一目标的链接。archive 则冻结正文、元数据、路径和已有 seal；任何内容操作都不能改、移、删或重新封存。具体格式与历史检查见[文档契约](../../assets/formats/document.md)。

`check --maintenance` 返回失配 scope、替代等维护候选，由作者选择具体动作；不按年龄、字数或配额自动清理，也不创建持久维护队列。

## 文档内容与分发

按主要读者与权威归属组织源码，以分发范围决定安装内容。`assets/` 集中产品运行资源，使源码、npm 包与 runtime 使用相同的资源树；宿主 skill 是该内容的安装投影。

| 唯一维护位置 | 内容与职责 | 分发范围 |
| --- | --- | --- |
| README | 产品概览与使用参考入口 | 仓库、npm |
| `docs/installation.md` | 使用者安装、确认、升级和修复的步骤 | 仓库、npm |
| `docs/maintainers/` 与 AGENTS | 设计理由、开发约束、验证与上游依据 | 仅仓库 |
| `assets/skills/` | 两个 skill 的工作流，以及各自专用的参考和示例 | npm、runtime 与宿主 skills 目录 |
| `assets/references/` | 共用命令行为、写入输入、生命周期操作与恢复 | npm、runtime |
| `assets/formats/` | 持久格式的 Schema、跨文件语义与兼容约束 | npm、runtime；Schema 同时作为 CLI 编译输入 |
| `assets/templates/` | 新 Note 的起草材料 | npm、runtime |

skill 编排动作并按分支指向参考；安装指南编排接入步骤并引用命令契约。参数和输入各有一个定义位置。文档契约与 Schema 分别定义跨文件规则和字段形状，模板不定义既有文档是否合法。维护设计解释取舍，产品参考说明运行规则。

专用资料就近放在所属 skill 中，共用资料保持单一编辑源。产品资源的本地链接必须在 `assets/` 内闭合，安装指南和 README 的链接必须在 npm 包内闭合；维护文档可以引用产品资源、源码与测试。

runtime 内保留完整 `assets/` 副本，以便离线重新安装和修复宿主 skill。宿主目录中的 skill 是受管产物：共享资源链接指向 runtime，专用资料链接指向该 skill 的安装目录。分发代码按源与目标的映射重算 Markdown 链接，目录结构知识集中于安装投影。生成副本不增加编辑源，也不作为项目定制入口。

项目使用单一 Notes 根目录，默认 `.agents/notes`；`--notes-dir` 同时决定配置、安装清单、runtime、local 和生命周期文档的位置。路径由统一布局对象生成，读取 Note 时排除 runtime 和 local。安装时按实际根目录替换文本资源中的命令与示例路径，再计算资产 hash；宿主 skills 使用各自规定的位置；常驻规则文件由项目维护。

## 资产所有权与版本治理

| 对象 | 所有者 | 更新边界 |
| --- | --- | --- |
| runtime、源索引、两个 skill、模板、文档契约、Git 受管块 | 工具包 | 同一个工具版本与 bundle hash，一起替换 |
| install.json | 安装器 | 记录具体版本、接入集合、精确资产路径及 hash，事务最后切换 |
| config.json、Note、archive manifest | 项目 | 配置文件缺失时才初始化；tool update 保留原字节与路径 |
| 全部 AGENTS / CLAUDE 与 Git 块外内容 | 项目 | 局部接入时保留原文 |
| local 草稿、journal、备份 | 本地运行状态 | Git 忽略；恢复或人工处置，不作为生效规则 |

工具使用一个 SemVer；`agent-note/1`、`agent-note-archive/1`、配置和安装清单各有独立格式。工具版本不决定旧 Note 是否有效。若需要扩展文档协议，使用新 format 并继续读取旧格式；新增模板要求不能成为旧文档的新必填项。

日常命令委派给项目锁定 runtime，保持检出后即可离线执行。install/tool update 只由 npm 包执行，版本选择和下载交给包管理器；项目帮助展示日常命令、hosts set、status 和 repair。运行来源集中识别，入口限制在交互和事务恢复之前完成。

tool update 只切换工具版本，相同版本完整时无改动、损坏时提示 repair。repair 保持版本与 bundle hash 不变，使用当前版本的原始文件恢复安装状态，避免同一个命令因调用入口不同而承担升级或修复两种职责。本地源文件必须与清单完整匹配；源文件损坏时从同版本 npm 包恢复，不从受损副本重新定义安装内容。

普通版本切换遇到受管损坏先要求 repair；repair 先备份完整原文、替换和差异摘要，备份失败不覆盖。未知文件保持原样，同名冲突预检失败。修复沿用同一套资产所有权、备份与事务规则。

项目定制使用配置或独立补充规则，避免复制并长期分叉受管 skill。配置固定为文档根与模板语言，不提供关闭冻结、路径保护等核心约束的政策 DSL。

## 事务、快照与可验证边界

内容操作、安装、升级和修复使用同一 checkout 的写锁、预期 hash 与 journal。预检后取得锁并复查所有输入，提交完成前再复核；失败回滚，中断可显式恢复。恢复只接受 journal 的 before/after 端点，外部编辑冲突保留现场。各 worktree 的锁不提供跨机器互斥，合并仍依靠身份、关系和可信基线校验。

完整资产与归档按原始字节 hash。Notes、完整受管文件和配置/安装清单设 `text eol=lf`；Git 受管块比较允许 CRLF 归一，存储保留项目换行与块外内容。原有 Git 属性冲突在写入前失败。

工作树、index、commit 的检查不混用文件。ref 固定解析为 SHA；调用者负责可信基线和验证器，快照中的脚本不会被执行。归档 seal 必须同时对照可信基线，否则正文和 seal 一起改写仍可能自洽。

首次归档只有来源字节能从基线或精确 source revision 重现时，独立 check 才能复核全过程。两端快照无法恢复的中间过程列入 review。退出 0 只说明操作完成或机械检查通过，不证明记录价值、完整吸收或模型理解。
