# 设计约束与依据

Agent Notes 以 DeepSeek Harness Notes 的治理原则为基础：保留有长期价值的决策理由，维护仍指导工程的记录，并冻结只需追溯的历史。固定上游来源见[上游依据](upstreams.md)。

## 规划与记录分别判断

工作规模决定是否需要规划，长期理由决定是否需要 Note。进入原生 Plan 不代表同意创建文档；Agent 提出记录建议并获同意，或用户显式要求后才进入记录。一次授权覆盖同一工作范围。

只有代码、测试、现有文档无法解释的长期“为什么、放弃了什么”才需要记录。机械性或局部 UI 改动可零 Note 完成；代码量少但改变兼容性、持久化或责任边界时仍需评估。命中判据而尚无授权时应提出建议，不能自动创建，也不能静默遗漏。

先查现有决定，再准备普通 Markdown 草稿；内容完整后由 create/update 写入。草稿不是 CLI 生命周期，不生成空壳 Note、免写文件或会话台账。相同 topic 只是候选线索，不证明属于同一决定。

必要 Note 与相关代码在同一个 PR 交付，可以分布在多个 commit；不能代码合并后再补写。纯提案、拒绝或文档维护可以独立提交。没有 PR 时，以团队一起检查并集成的完整变更范围作为交付单元。

## 入口、skill 与 CLI 的分工

根入口只规定何时查询：规划相关变更或首次编辑前按路径/主题运行 context；范围扩大时重查；按指针读取正文；交付前 check。context 每次重建内存索引，不持久化查询缓存或手工中心索引。无路径或主题时只返回 global 记录及其现行依赖。

| 层次 | 责任 | 原因 |
| --- | --- | --- |
| AGENTS / CLAUDE 静态入口 | 读取时机、记录入口、交付检查 | 常驻内容短，避免全库正文进入上下文 |
| agent-note | 资格判断、复用、撰写、事实维护、交付或拒绝 | 这些动作围绕当前决定，需要作者理解上下文 |
| agent-note-maintenance | 替代、剩余价值复核、吸收、归档和条件清理 | 存量维护的触发与完成条件不同 |
| CLI | 身份/路径、输入、格式、关系、转换、引用、冻结和事务 | 可确定的约束由同一套脚本执行 |
| 作者与评审 | 长期价值、决定身份、实际交付和完整吸收 | 字段完整不能证明语义真实 |

安装、查询和普通 Plan 不另设 skill。`.agents` / `.claude` 只选择静态资产位置；双目标时 Claude 导入 AGENTS 共用路由。现有独立行直接导入可复用，代码示例不算生效导入。Claude 单目标仍提供自身路由，并在新建入口时继承现有 AGENTS 规则。

静态规则无法证明 Agent 已读或理解正文。CLI 提供可独立调用的 check；需要阻断合并时，由项目接入已有检查流程并选择可信基线。产品不承担宿主 hooks、会话事件或平台配置管理。

## 生命周期选择

| 工程情形 | 行为与理由 |
| --- | --- |
| 尚未交付但已有完整提案 | proposed；已同意方向不等于实现完成，无需 accepted 状态 |
| 新决定已实现并验证 | 可直接创建 implemented，不强制先建 proposed |
| 同一提案交付 | 转 implemented，写实际决定、后果和验证 |
| 未采纳或停止推进 | 转 rejected，保留原提案和真实拒绝理由，无需 withdrawn 状态 |
| 路径或实现机制改变，决定不变 | 维护原 Note 的事实与作用范围 |
| 决定改变 | 新建并互链；partial/full 表达替代范围，proposed 替代只表示意图 |
| 已交付且仍能指导工程 | 保持活跃；完成本身不是归档条件 |
| 不再有未来指导价值，但值得历史追溯 | 归档 implemented；保留 implemented 元数据状态并冻结 |
| rejected 已无防错价值 | 提供理由并处理全部活跃引用后可清理 |
| implemented 的全部独有内容已被现行 owner 吸收 | 提供 coverage、承接者和引用去向后可清理 |

完整替代只表示旧决定不再执行，不证明其独有理由、替代方案、后果、验证和覆盖缺口已被吸收。部分替代的旧记录仍需维护剩余指导范围。不得以“Git 历史里还有”为由省略内容承接。

rejected 以 Git 基线保护原提案和拒绝理由，仅维护路由、关系和可验证为同一目标的链接。archive 则冻结正文、元数据、路径和已有 seal；任何内容操作都不能改、移、删或重新封存。具体格式与历史检查见[文档契约](../contracts/document.md)。

`check --maintenance` 返回失配 scope、替代等维护候选，由作者选择具体动作；不按年龄、字数或配额自动清理，也不创建持久维护队列。

## 资产所有权与版本治理

| 对象 | 所有者 | 更新边界 |
| --- | --- | --- |
| runtime、两个 skill、模板、文档契约、入口受管块 | 工具包 | 同一个工具版本与 bundle hash，一起替换 |
| install.json | 安装器 | 记录具体版本、目标、精确资产路径及 hash，事务最后切换 |
| config.json、Note、archive manifest | 项目 | 配置文件缺失时才初始化；upgrade 保留原字节与路径 |
| AGENTS / CLAUDE 与 Git 规则的非受管内容 | 项目 | 局部接入时保留原文 |
| local 草稿、journal、备份 | 本地运行状态 | Git 忽略；恢复或人工处置，不作为生效规则 |

工具使用一个 SemVer；`agent-note/1`、`agent-note-archive/1`、配置和安装清单各有独立格式。工具版本不决定旧 Note 是否有效。若需要扩展文档协议，使用新 format 并继续读取旧格式；新增模板要求不能成为旧文档的新必填项。

日常命令委派给项目锁定 runtime，init/upgrade 使用本次调用的完整工具包。这样其他开发者检出项目后使用相同规则，无需全局版本一致或联网查询。精确版本选择交给包管理器，CLI 不再维护下载器。

升级只替换清单列出的受管资产；手改先备份原文件与 diff，备份失败不覆盖。未知文件保持原样，同名冲突预检失败。回退也只切换兼容的工具资产，不能回退用户文档。新安装不隐式接管其他格式或旧 agent-governance 资产。

项目定制使用配置或独立补充规则，避免复制并长期分叉受管 skill。配置固定为文档根与模板语言，不提供关闭冻结、路径保护等核心约束的政策 DSL。

## 事务、快照与可验证边界

内容操作、安装和升级使用同一 checkout 的写锁、预期 hash 与 journal。预检后取得锁并复查所有输入，提交完成前再复核；失败回滚，中断可显式恢复。恢复只接受 journal 的 before/after 端点，外部编辑冲突保留现场。各 worktree 的锁不提供跨机器互斥，合并仍依靠身份、关系和可信基线校验。

完整资产与归档按原始字节 hash。Notes、完整受管文件和配置/安装清单设 `text eol=lf`；入口受管块比较允许 CRLF 归一，存储保留项目换行与块外内容。原有 Git 属性冲突在写入前失败。

工作树、index、commit 的检查不混用文件。ref 固定解析为 SHA；调用者负责可信基线和验证器，快照中的脚本不会被执行。归档 seal 必须同时对照可信基线，否则正文和 seal 一起改写仍可能自洽。

首次归档只有来源字节能从基线或精确 source revision 重现时，独立 check 才能复核全过程。两端快照无法恢复的中间过程列入 review。退出 0 只说明操作完成或机械检查通过，不证明记录价值、完整吸收或模型理解。
